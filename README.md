# Tera

> *Tera* (Indonesian): to officially calibrate a measuring instrument.

**Tera calibrates your pricing.** Design a plan, run a virtual customer through upgrades, trials, coupons, seats, metered usage and taxes, and see every invoice to the cent before a real customer does. Then prove it: every reference scenario is replayed in a real Stripe test-mode account and must match line by line.

- **Live:** https://tera-orpin-three.vercel.app
- **Stripe parity:** [/parity](https://tera-orpin-three.vercel.app/parity). **All 81 golden timeline scenarios match Stripe to the cent, in both classic and flexible billing mode, including Stripe's new pause and resume (API 2026-09-30.endive).**
- **API:** [/reference](https://tera-orpin-three.vercel.app/reference) (Scalar, interactive) · [OpenAPI](https://tera-orpin-three.vercel.app/api/openapi.json)
- **MCP for AI agents:** `claude mcp add --transport http tera https://tera-orpin-three.vercel.app/api/mcp`
- **PRD:** [`docs/PRD.md`](docs/PRD.md). Billing rules R1–R21, invariants I1–I6, every feature tagged SHIPPED.

## Why it exists

Founders are afraid to touch pricing. A mid-cycle upgrade, a coupon or a tax rule produces invoices nobody previewed, and mistakes are found by customers on their card statements. Stripe executes billing; Tera lets you *simulate* it across customers and time first. It never moves money.

## How correctness is established

1. **Rules first.** [`docs/PRD.md`](docs/PRD.md) states each billing rule, for example R3 proration: `−round(old × remaining / period)` and `+round(new × remaining / period)`.
2. **Golden scenarios by hand.** [`golden/scenarios.json`](golden/scenarios.json) holds 84 scenarios. Their expected invoices are derived by hand, with the math written next to them. They are **never** generated by the engine.
3. **Stripe is the oracle.** [`scripts/verify-golden.mts`](scripts/verify-golden.mts) replays every timeline scenario in Stripe test mode. It uses test clocks, classic billing mode, API `2026-09-30.endive`, and Stripe Meters for usage. It diffs date, lines, subtotal, discount, tax, total, starting balance and amount due. Matches are marked `verified`, and the evidence (invoice ids, test clock) is committed in [`golden/parity/`](golden/parity).
4. **Stripe corrected us, and we kept the receipts:**
   - **S11:** a coupon applied in the same second as subscribing discounts the *next* invoice. Stripe finalizes the first invoice at creation.
   - **S21:** new subscriptions default to *flexible* billing mode. Tera models *classic*, and that is now rule R12.
   - **S30–S34:** a custom timeline sent through **Verify in Stripe** exposed two engine bugs. A credit after a used-up `once` coupon refunds the discounted price actually paid, and `change_price` without a quantity resets seats to 1 (R13). Our hand derivation of S33 was wrong too, and Stripe fixed it.
5. **Differential fuzzing.** [`scripts/fuzz-parity.mts`](scripts/fuzz-parity.mts) generates seeded random timelines (month-end anchors incl. Feb 29, random times of day, trials, seat and plan changes, interval switches, percent and amount_off coupons, inclusive and exclusive tax, cancellations, USD and JPY) and replays each in Stripe. The first 60 timelines found **7 rule gaps** that 31 hand-written scenarios had missed. Each gap was confirmed with a targeted Stripe probe ([`scripts/probe-stripe.mts`](scripts/probe-stripe.mts)) and pinned as a hand-derived golden (S35–S42). All 60 now match. Its **first nightly CI run found an 8th** (S43, a no-op `always_invoice` change still invoices pending prorations). The engine then grew four more Stripe actions (`proration_behavior: none`, ending a trial early, undoing a scheduled cancel, cancelling immediately); a probe showed Stripe credits the *current* item after an unprorated change, not what was paid (R14), and each action is pinned as a verified golden (S44–S49) and fuzzed nightly. The next 30 fuzzed timelines found that a `repeating` coupon lasts its months in calendar time, not a count of invoices (S50). Two more actions, resetting the billing anchor (`billing_cycle_anchor: now`) and removing a coupon, came with Stripe probes (R15, S51–S53), plus S54 guarding a credit after two interval changes under an `amount_off` coupon. The next fuzz batch found a 1-cent diff on a credit of exactly 11257.5: Stripe prorates the *unit* price to 12 decimals before multiplying by seats, so 5003.333333333333 × 3 × 75% lands just under the tie (S55, S56, after four targeted probes). The batch after that found a coupon applied at the exact renewal instant: Stripe copies the discount onto the renewal draft when it creates it, so the coupon starts with the next invoice (S57). Then **flexible billing mode**, Stripe's default for new subscriptions since 2025, which Tera had not modelled: replaying all 54 classic goldens with `billing_mode: flexible` made 16 differ, and the differences give R16 (credits refund each original debit with gross and discount rounded apart, the anchor never resets on an interval change, an anchor reset nets out). Eight hand-derived flexible goldens (S58–S65) are verified, and the fuzzer takes a mode (`fuzz-parity.mts 60 40000 flexible`). Its first flexible batch found one more cent: a proration debit is credited from its rounded gross and rounded discount, not its net (S66). Then refunds on immediate cancellation (Stripe `prorate` + `invoice_now`, R17): probed in both modes, pinned as S67 and S68, and half of the fuzzer's immediate cancellations now ask for one. The second flexible fuzz batch found two more: an amount due under Stripe's 50-cent minimum is carried to the next invoice instead of charged (R18, S69, both modes), and after a `none` yearly → monthly change a later credit stops at the monthly period end (S70). Cancelling on a date (`cancel_at`, R19) came with ten probes across both modes: a final credit inside the period, a shortened last renewal in a later one (S71–S73). Billing on a fixed day (`billing_cycle_anchor` at creation, R20): the stub before the first billing date is prorated over the period that ends on it, one interval counted from the start (S74–S76). The next fuzz batch, aimed at the new actions, found three more: that interval is counted from the start even at month end (S77), a coupon-free debit is still credited as a $0 line (S78), and a percent discount on a proration comes off the rounded gross, 7135.5 → 7136 (S79). Pause and resume (R21), new in Stripe API 2026-09-30.endive, came with five probes: the credit waits for the resumption invoice by default, is its own credit invoice with `invoicing_behavior: invoice`, and an unchanged anchor bills the rest of the cycle at the next renewal (S80–S84); the flexible fuzzer now pauses and resumes a third of its subscriptions. It runs nightly in [`stripe-parity.yml`](.github/workflows/stripe-parity.yml) with fresh seeds. The same workflow replays every golden scenario in Stripe on any PR that touches the engine.
6. **Verify your own timeline.** "Verify in Stripe" in the simulator, or `POST /api/parity { timeline, catalog? }`, replays *any* timeline (up to 15 events, 2 years) in a fresh Stripe test clock and diffs it to the cent.

## Tests that run themselves

| Layer | What runs | When |
|---|---|---|
| Unit (Vitest) | Engine vs all golden scenarios; invariants I1 (totals add up, integer money), I2 (credit ≤ paid), I5 (deterministic), I6 (amount due ≥ 0), checked on the goldens **and on 5,000 seeded random timelines** (credit carried invoice to invoice, rejections are reasons not crashes); Stripe-rejected timelines; CSV and share-link parsing | `npm test` |
| **TestSprite UI** (GitHub App) | Plans that assert exact amounts in the browser: golden badge, edits, out-of-order dates, locales, credit balance, trial changes, migration math, parity page, builder, MCP page | **Every PR** against its Vercel preview; branch protection requires `TestSprite V3` |
| **TestSprite API** (CLI in Actions) | Golden contract (every scenario through `/api/simulate`, to the cent); R10/R11 behaviour; 400/422/404; parity evidence | Every push to `main`, nightly, on demand. See [`.github/workflows/testsprite-api.yml`](.github/workflows/testsprite-api.yml) |
| Stripe parity | Every golden scenario replayed in real Stripe test clocks | Every PR touching the engine (`stripe-parity.yml`), `node scripts/verify-golden.mts --mark`, live from `/parity` |
| Differential fuzzing | 24 fresh random timelines per billing mode (classic and flexible), Tera vs Stripe | Nightly (`stripe-parity.yml`), `node scripts/fuzz-parity.mts [count] [seed] [classic\|flexible]` |
| **Playwright user journeys** | A user who only clicks, types (dates key by key), picks from dropdowns, picks a CSV file and downloads one: builds a flexible fixed-billing-day timeline from scratch, shares it, exports it, switches locale, **verifies it live in Stripe**; adds a price in the builder and bills it; runs the migration planner with grandfathering and a CSV import; opens Stripe evidence on `/parity`; MCP and API pages. Expected amounts are hand-derived. Its first run caught two real bugs: typing a date froze the tab (year 0202 = 21,901 renewals), then the guard ate the keystrokes | **Every PR** against its Vercel preview and every push to `main` against production ([`e2e.yml`](.github/workflows/e2e.yml), run video kept as an artifact), `node e2e/user-journeys.mjs <url>` |

The TestSprite suites are versioned as code in [`testsprite/`](testsprite): UI plans in `plans/*.json` and API tests in `api/*.py`. Each one is created with `testsprite test create`.

**What a green check means:** every golden invoice still matches to the cent in every currency, through the UI and the API, and the API still rejects what Stripe rejects.

## Develop

```bash
npm install
npm run dev                                  # http://localhost:3000
npm test                                     # engine vs golden scenarios + invariants
node scripts/verify-golden.mts --mark        # replay in Stripe test mode (needs STRIPE_SECRET_KEY=sk_test_… in .env.local)
TERA_BASE_URL=http://localhost:3000 python testsprite/api/golden_contract.py
```

Stack: Next.js 16 (App Router, Cache Components), React 19, TypeScript, Tailwind 4, Vitest, `stripe@23`, `mcp-handler@2`, Vercel.
